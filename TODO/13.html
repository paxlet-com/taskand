Wszystko jest zasobem URI — przeglądarka, strona, artefakt, sesja — więc dostęp jest zawsze identyczny.

Wysłanie zadania „zaloguj się i przeanalizuj stronę” uruchamia łańcuch czterech procesów z trzech paczek. Każdy krok to wywołanie proc:// URI z JSON-em na stdin → JSON na stdout: zadanie logowania woła proces przeglądarki, ten woła proces nawigacji po stronie, a ten — proces analizy zawartości. Żaden proces nie importuje kodu innego; runtime (docker-playwright / browserbase / node) dobiera binding z katalogu, a dane między krokami przepływają jako artefakty URI (nie pliki inline).

Dlaczego to jest samostandardyzujące: nowa paczka (np. z lepszym OCR, innym silnikiem przeglądarki) podmienia wpis w proc-catalog.json — łańcuch się nie zmienia, bo woła URI, nie implementację. Ewolucja runtime'u (docker → wasm → zdalni runnerzy) to dopisanie wiersza w bindingu. Symulacja niżej uruchamia cały łańcuch krok po kroku.
ZADANIE „zaloguj się i przeanalizuj portal.example.com” ↓ koperta CloudEvents → proc://taskand.dev/flow/login/v1 ← paczka: taskand-flow-login ↓ woła URI (nie kod!): proc://taskand.dev/browser/session/v1 ← paczka: taskand-browser [runtime: docker-playwright | browserbase | local] ↓ sesja = zasób URI: session://browser/s-8f3a ← dostęp przez URI ↓ woła URI: proc://taskand.dev/web/navigate/v1 ← paczka: taskand-web-ops ↓ wynik = artefakt URI: artifact:page-content@sha256:9f3c… ← CAS, nie inline ↓ woła URI: proc://taskand.dev/web/analyze/v1 ← paczka: taskand-web-ops ↓ wynik końcowy: {summary, links, keywords}
01princip — wszystko zasobem URIjedyny interfejs dostępu

Niezależnie od tego, co stoi za zasobem (kontener z Playwrightem, zdalna przeglądarka, plik w CAS, sesja z cookie) — dostęp jest zawsze identyczny: URI → binding → runtime → JSON→JSON. To jest gwarancja, że paczki mogą się samostandardyzować: nowa implementacja zasobu podmienia wpis w katalogu, a wszyscy konsumenci działają dalej.
