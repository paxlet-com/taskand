URI = tożsamość procesu · binding = jak wykonać (node/docker/make/remote)
katalog z hashami · git: obserwacja ≠ wykonanie ≠ publikacja · fail-closed: JSON stdin → JSON stdout

Przejmuję z Twojego uriprocess to, czego taskand potrzebował od początku: URI jako tożsamość procesu, nie adres usługi.

Nowy schemat proc://<organizacja>/<ścieżka>/<wersja> adresuje wykonywalną zdolność, nie kontener: proces ma standardowy wpis (bin.mjs: JSON na stdin → JSON na stdout, kody wyjścia 0/1/2, fail-closed), a binding deklaruje, jak go uruchomić w dowolnym runtime — node, docker, make, ssh. Katalog z hashami (jak Twój native-catalog.json) trzyma rewizje git i digesty; obserwacja dokładnej rewizji (make observe) jest osobnym uprawnieniem od wykonania (make run) i publikacji.

Dlaczego to rozwiązuje ewolucję runtime: dziś taskand wykonuje zdolności przez Dockerfile — jutro może przez WASM, zdalnych runnerów albo natywne pakiety. Z proc:// zmiana runtime'u to dopisanie wiersza w bindingu: wywołujący (koperty, router /route z v0.12, supervisor) nie zmienia ani jednej linijki. Spróbuj w sekcji 02: ten sam URI, ten sam JSON — pięć runtime'ów (w tym „przyszły”).

04symulacja · kontrola git — observe ≠ run ≠ pack (rozdział uprawnień)jak Twój Guard: obserwacja bez prawa wykonania

Trzy operacje na tym samym procesie: observe (odczyt dokładnej rewizji z git — zero prawa wykonania), run (wykonanie — osobny grant, fail-closed), pack (archiwum do dist/ + hashe do katalogu — trzecie uprawnienie). To wprost Twoja zasada „grants no execution or publication authority”.
