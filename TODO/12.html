v0.14 · finalny standard paczki · 1 paczka = N procesów · wspólny szkielet

proces = jednostka WYKONANIA (proc://, kontrakt JSON→JSON)
paczka = jednostka WERSJONOWANIA (git, tag, ewolucja, granty, twin)

Jedna paczka zawiera wiele procesów — bo proces i paczka odpowiadają za różne rzeczy.

Proces (proc://taskand.dev/…/v1) wykonuje jedno zadanie z kontraktem: JSON na wejściu → JSON na wyjściu, fail-closed, własna wersja v1/v2. Paczka (kapsuła = repozytorium git z tagiem capsule-v…) wersjonuje, ewoluuje i broni (granty, twin, deploy) całą rodzinę procesów + wspólne artefakty. Między paczkami procesy wołają się wyłącznie przez URI — nigdy przez import kodu: paczka jest granicą kodu, URI granicą wołania.

Podwójne wersjonowanie (celowe): ewolucja procesu = nowy URI (v1 → v2, stare immutable — jak parallel-major koperty); ewolucja paczki = nowy tag git (może zmienić atomowo wiele procesów, grants, schematy). Minimalna paczka = 1 proces; duża = dziesiątki. Standard nie wymusza granularności — wymusza szkielet.

03wołania między procesami i podwójne wersjonowanieURI granicą · tag granicą atomowości

Procesy within paczki też wołają się przez URI (nie przez import) — dzięki temu refaktor wewnętrzny nie zmienia zachowania na zewnątrz, a testy kontraktu łapią każdy przełom.
