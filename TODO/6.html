v0.8 · ewolucja oddzielona od procesu · aplikacja ≠ deweloper · restart przez Makefile

paczka aplikacji: repo read-only w runtime · paczka dewelopera: git rw na celach (grants)
ewolucja = zadanie w kolejce · restart: make restart (supervisor) · rollback: git revert

Tak — ewolucja jako osobna paczka i zwykłe zadanie. Aplikacja działa, deweloper zmienia, Makefile restartuje.

Paczka aplikacji taskand w runtime montuje własne repozytorium read-only — nie ma ewolutorów, nie modyfikuje sama siebie. Zmianę realizuje odrębna paczka taskand-developer: bierze zadanie ewolucji z tej samej kolejki co zwykłe zadania (priorytet evolution — ustępuje user-blocking), pracuje na klonie celu przez git (branch → edycja → commit → walidacja → merge --no-ff → tag), a potem żąda restartu — supervisor wykonuje make restart w paczce aplikacji. Aplikacja wstaje na nowej wersji.

Co się zmieniło względem v0.7: ewolutory wyleciały z paczki aplikacji (jej compose montuje .:/taskand/package:ro — zapis DENY w runtime); ewolucja jest typem zadania (evolve-function / evolve-docs / evolve-line), nie procesem wewnętrznym; developer ma grants na repozytoria celów i prawo request-restart — sam nigdy nie restartuje; rollback = git revert + make restart (historia naprzód, audyt zachowany).

01podział praw — aplikacja kontra deweloperkto co może — i czego NIE może

Dwie paczki, dwa zestawy praw. Kluczowe wiersze: aplikacja nie pisze do własnego repo w runtime (brak samomodyfikacji), deweloper nie ma gniazda dockera (nie uruchamia nic sam — może tylko poprosić o restart).
