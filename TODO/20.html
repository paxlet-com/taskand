inne paczki oddkrywają przez katalog → konsumują przez URI

Każda paczka taskand może być rejestrem — bo już ma katalog procesów. Wystarczy dodać proces serve.

Skoro każda paczka ma proc-catalog.json i katalog proc/, to wystarczy jeden dodatkowy proces (proc://…/registry/serve/v1) — i paczka staje się rejestrem, który może serwować swoje procesy innym. Developer z dostępem do LLM może tworzyć nowe procesy i rejestrować je w swoim registry — a inne paczki odkrywają je przez federowaną wymianę URI (kopia CloudEvents jako protokół wymiany).

Kluczowa zmiana: URI procesu zyskuje prefiks rejestru — proc://taskand.dev/developer/summarize/v1 oznacza proces w registry developera. Supervisor routuje: lokalne registry → bezpośrednio; zdalne registry → przez wymianę (envelope). Developer staje się żywą biblioteką procesów tworzonych przez LLM.
// federacja rejestrów — każda paczka = registry registry://taskand.dev/core ← paczka: taskand-core proc: hello-world, analyze-text, deploy ← procesy w TEJ paczce registry://taskand.dev/developer ← paczka: taskand-developer proc: evolve-feature, twin-runner ← + NOWE (tworzone przez LLM!) LLM: glm-5.3 (klucz z .env, runtime-only) ← źródło nowych procesów registry://taskand.dev/web ← paczka: taskand-web proc: chat-serve, evolve-request // WYMIANA między rejestrami (federacja): web ──discover──→ registry://developer/.well-known/catalog web ──pull──────→ proc://developer/summarize/v1 (z hashami ✓) web ──call──────→ printf | node …/bin.mjs (identycznie!) // procesy z innych rejestru — pełne URI: proc://taskand.dev/core/hello/v1 ← lokalny proc://taskand.dev/developer/summarize/v1 ← z registry developera // klucz: wywołujący zawsze widzi to samo (URI + JSON→JSON)

02jak optymalnie budować takie organizmy — wzorce federacji3 wzorce

Federacja rejestrów to sieć organizmów. Każdy może być rejestrem, ale nie każdy musi — wybór wzorca zależy od skali i potrzeb.
